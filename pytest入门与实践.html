01pytest 是什么

pytest 是 Python 生态中广泛使用的测试框架。它适用于从小型单元测试到集成测试的多种场景，也能运行许多基于 unittest 的现有测试。

低门槛普通函数配合原生 assert 就能表达预期。
清晰的失败诊断自动展示断言表达式中的实际值，减少定位时间。
Fixture 机制复用数据与资源准备逻辑，并管理生命周期和清理。
灵活扩展参数化、标记与插件适应不同规模的项目。
框架提供测试运行与组织能力，不会自动判断需求是否覆盖充分。测试质量仍取决于清晰的预期、有效的边界分析和可靠的测试数据。

02安装与第一个测试

推荐在项目虚拟环境中安装，避免依赖污染系统 Python：

python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# macOS / Linux: source .venv/bin/activate
python -m pip install pytest

创建 test_calculator.py，写下一个普通函数测试：

def add(a: int, b: int) -> int:
    return a + b


def test_add_two_positive_numbers():
    assert add(2, 3) == 5

从项目根目录运行：

python -m pytest

成功时通常会看到 1 passed。使用 python -m pytest 可明确通过当前 Python 环境执行模块；也可直接使用 pytest 命令。

03测试发现与命名

pytest 默认递归查找遵循约定的测试文件、类和函数：

  • 文件名通常是 test_*.py 或 *_test.py。
  • 函数名以 test_ 开头。
  • 测试类以 Test 开头，且通常不定义 __init__。
  • 类中的测试方法以 test_ 开头。
pytest --collect-only
pytest tests/test_user.py
pytest tests/test_user.py::TestUser::test_create_user

第一条命令只检查收集结果；后两条分别运行指定文件和节点。函数名应描述行为与场景，例如 test_rejects_expired_token，而不是 test_case_03。采用 src/ 布局时，建议将产品代码作为已安装包导入，并在项目配置中设置测试路径，减少工作目录造成的导入差异。

04assert 与失败信息

用 Python 原生 assert 清楚地写出期望：

def test_discounted_price():
    price = 100
    discount = 0.2
    final_price = price * (1 - discount)

    assert final_price == 80
    assert final_price < price

失败时 pytest 会重写断言表达式，展示参与比较的值。测试应验证使用者关心的行为，而不是照搬被测函数的内部算法。浮点数建议使用容差比较：

assert actual == pytest.approx(0.3)

05Fixture：组织前置条件和清理

测试函数把 fixture 名称写作参数，pytest 会查找对应 fixture 并注入其返回值。Fixture 也可以依赖其他 fixture，组合出清晰的准备流程。

import pytest


@pytest.fixture
def user_record():
    return {"id": 7, "name": "Lin", "active": True}


def test_user_is_active(user_record):
    assert user_record["active"] is True

Fixture 的作用范围

scope生命周期常见用途
function（默认）每个测试函数隔离性强的临时数据
class一个测试类类内共享且安全的状态
module一个测试模块模块级昂贵准备
package一个包包内共享资源
session整次 pytest 会话只读客户端、公共静态资源

作用范围越大，创建次数越少，但共享状态和测试耦合风险越高。只有资源能安全共享时才扩大范围。

用 yield 管理清理

@pytest.fixture
def temp_connection():
    connection = open_connection()
    yield connection
    connection.close()

yield 前准备资源，之后释放资源。多步初始化时，应让每一步准备都能对应清理，避免后续初始化失败留下半初始化资源。放在 conftest.py 的 fixture 可被该目录及子目录中的测试发现，无需显式导入；共享 fixture 应放在合适目录层级，职责保持清晰。

06参数化：用一份测试覆盖多组数据

逻辑相同而输入不同的场景，可通过 @pytest.mark.parametrize 展开为独立用例：

import pytest


@pytest.mark.parametrize(
    "text, expected",
    [
        ("hello", 5),
        ("", 0),
        ("你好", 2),
    ],
)
def test_character_count(text, expected):
    assert len(text) == expected

每组参数独立报告，失败时能看出是哪组数据出错。边界值、非法输入和等价类都适合参数化。尽量给参数命名，避免把所有组合塞进一个测试；组合过多时按风险取舍，防止套件膨胀。Fixture 也可参数化；需要单独处理某条输入时，可用 pytest.param(..., marks=...)。

07Marker：给测试分类与筛选

内置 marker 可以描述跳过条件或预期失败：

import pytest


@pytest.mark.skip(reason="功能尚未支持")
def test_future_feature():
    ...


@pytest.mark.skipif(not is_windows(), reason="仅 Windows 支持")
def test_windows_behavior():
    ...


@pytest.mark.xfail(reason="上游缺陷尚未修复")
def test_known_bug():
    ...

项目也可以定义 slow、integration 等自有标记，再用 pytest -m "not slow" 按类型筛选。建议在配置文件注册自定义 marker，减少拼写错误并让意图清楚。定期清理过期标记 长期失败用例不应被无限期跳过或标成预期失败。

08常用内置能力

预期异常

使用 pytest.raises 检查异常类型，必要时匹配消息：

def test_invalid_age_is_rejected():
    with pytest.raises(ValueError, match="age must be positive"):
        create_profile(age=0)

把操作放在 with 内最小范围，避免其它代码意外触发同一异常而误通过。

临时文件与目录

tmp_path 为每个测试提供独立临时目录：

def test_export_writes_json(tmp_path):
    output = tmp_path / "report.json"
    export_report(output)

    assert output.exists()
    assert '"status": "ok"' in output.read_text(encoding="utf-8")

这样不必在仓库中维护和清理临时文件。

Monkeypatch

内置 monkeypatch fixture 可以临时替换属性、环境变量、字典项或工作目录，并在测试结束后恢复：

def test_reads_api_key_from_environment(monkeypatch):
    monkeypatch.setenv("API_KEY", "test-key")
    assert load_api_key() == "test-key"

优先替换系统边界（时间、网络、环境变量、文件系统入口），避免过度模拟内部细节。

09配置与命令行

pytest 支持 pyproject.toml、pytest.ini、tox.ini 等配置。新项目可将设置集中在 pyproject.toml：

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-ra"
markers = [
  "slow: 运行时间较长的测试",
  "integration: 需要外部服务或多个组件的测试",
]
命令用途
pytest运行发现到的测试
pytest -q简洁输出
pytest -v显示每个用例名称
pytest -x第一次失败后停止
pytest --maxfail=2最多遇到两次失败后停止
pytest -k "user and not slow"按名称表达式筛选
pytest -m integration按 marker 筛选
pytest --collect-only只收集，不执行
pytest --durations=10显示最慢的若干用例
pytest --tb=short较短的回溯信息

命令可以组合，例如 pytest -q -m "not slow"。CI 中应保留清晰的失败信息；-x 适合快速反馈，但不一定适合作为唯一完整回归运行方式。

10推荐项目结构与实践

my_project/
├── pyproject.toml
├── src/
│   └── my_project/
│       └── calculator.py
└── tests/
    ├── conftest.py
    ├── unit/
    │   └── test_calculator.py
    └── integration/
        └── test_api.py
  1. 先测可观察行为。输入、输出、状态变化和错误处理比私有实现细节稳定。
  2. 每个测试可以独立运行。避免依赖执行顺序或共享可变数据。
  3. 让失败容易诊断。测试名描述场景，断言定位明确，数据有代表性。
  4. 管理外部依赖。隔离网络、数据库、时间等边界；集成测试使用可控环境。
  5. 合理分层。快速单元测试和较慢集成测试分别组织，按需选择运行集合。
  6. 自动化运行。在 CI 中安装项目依赖并运行测试，失败时保留日志。
  7. 按需添加插件。插件扩展能力，也带来依赖和维护成本。

11常见问题

为什么没有发现测试？

检查文件名和函数名是否符合约定，确认运行目录及配置中的 testpaths，再运行 pytest --collect-only -q 查看收集结果。

为什么本地能导入，CI 却报模块找不到？

本地工作目录或 PYTHONPATH 可能偶然提供了导入路径。将项目规范安装到虚拟环境，统一 CI 工作目录和安装步骤，并检查 src/ 布局及配置。

为什么测试之间互相影响？

常见原因是共享可变状态、数据库记录未清理、临时文件重名、环境变量未恢复，或测试依赖运行顺序。使用 function-scope fixture、独立数据标识和可靠清理修复根因。

单元测试还是端到端测试？

两者解决的问题不同。单元测试反馈快、定位明确；集成或端到端测试验证更多真实组件的协作，但成本和环境复杂度较高。按风险分层组合，避免期待一种测试覆盖所有风险。

12小结与官方资料

pytest 从简单的 assert 起步，借助 Fixture 复用准备逻辑，用参数化覆盖输入空间，再通过标记和配置组织运行集合。框架提供结构与反馈；可靠的测试来自独立、明确、贴近用户行为的验证。
